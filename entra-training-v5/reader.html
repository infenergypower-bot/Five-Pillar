SC-900 · Security concepts

Identity, authentication and authorization

Visual analogy

A museum badge identifies the visitor; the ticket scanner authenticates it; the exhibit permissions authorize which doors open.

Concept

An identity is a record representing a person, device or application. Authentication is evidence that a claimant controls that identity. Authorization evaluates whether that already-authenticated identity can perform a requested action. An identity provider (IdP) creates and validates identities; a service provider relies on its assertions or tokens. Never equate a successful sign-in with permission to every resource.

How it works and why

Microsoft Entra ID is a cloud identity provider and directory. Active Directory Domain Services (AD DS) is a Windows directory for many on-premises authentication and policy workloads. A tenant is the identity boundary; a user object is one principal within that tenant. Modern authentication may use tokens rather than sending a password to each application.

Worked scenario

Avery signs in to the company directory, but cannot open Finance Reports until the report application or a group grants an appropriate role. A correct password does not confer Finance permissions.

Practice sequence

  1. Identify the principal requesting access
  2. Identify the system that verifies the principal
  3. Identify the resource and its owner
  4. Determine the specific permission needed
  5. Test access for both authorized and unauthorized users
Watch out

Mistake: saying MFA is authorization. MFA strengthens authentication; role assignment and app policy determine authorization.

SC-900 · Security concepts

Zero Trust, shared responsibility and defense in depth

Visual analogy

An airport checks the boarding pass again at each security boundary, even if the traveler passed the previous checkpoint.

Concept

Zero Trust is not a product. The principles are verify explicitly, use least privilege and assume breach. Shared responsibility means cloud providers secure some layers while customers still own their data, identities, access policies and workload configurations. Defense in depth uses multiple independent controls so one failure is not catastrophic.

How it works and why

A practical identity posture combines phishing-resistant sign-in, conditional access, limited administrator rights, logging, approvals and recurring access reviews. Encryption protects data confidentiality; hashing produces a one-way digest used for verification or integrity depending on context. Governance, risk and compliance (GRC) aligns controls with business obligations and risk tolerance.

Worked scenario

A stolen employee password should not immediately grant payroll data access: MFA or a passkey, a managed-device requirement, sensitive app entitlements and risk monitoring provide different layers of resistance.

Practice sequence

  1. Draw five security layers protecting one payroll app
  2. Mark which duties belong to your organization and the provider
  3. Choose a least-privilege access model
  4. Define a signal that should trigger extra verification
  5. Describe what evidence an auditor could inspect
Watch out

Zero Trust does not mean block everything; it means continually make access decisions using appropriate signals.

SC-900 · Microsoft Entra

The Entra family and identity types

Visual analogy

A directory is the employee roster; a tenant is the company campus; groups are departments; app identities are service badges for machines.

Concept

Microsoft Entra ID provides cloud authentication, authorization foundations and directory information. Member users, guest identities, service principals and managed identities serve different purposes. Hybrid identity connects existing AD DS accounts with cloud identity; the directory source of authority matters for updates and troubleshooting.

How it works and why

Separate access management from identity protection and governance: Conditional Access decides the conditions of sign-in; ID Protection evaluates certain identity risk signals; governance manages who receives and retains access; Privileged Identity Management (PIM) controls time-bound elevated permissions. Features and licenses differ: do not assume that every lab capability is free in a real tenant.

Worked scenario

A contractor invited as a guest can collaborate with a project team without receiving a permanent full employee identity. A background Azure function should use a managed identity rather than a shared human account when supported.

Practice sequence

  1. Classify four sample principals as member, guest or workload
  2. Find users and groups in the practice tenant
  3. Identify a feature that decides sign-in conditions
  4. Identify a feature that reviews continuing access
  5. Explain which identity should own an automated workload
Watch out

An enterprise application object (service principal) is not identical to its application registration; they represent different parts of an application’s identity.

SC-900 · Microsoft security

Azure security services and Microsoft Defender

Visual analogy

A secure office needs perimeter gates, locked rooms, cameras, incident investigators and a disaster plan—not a single giant padlock.

Concept

Azure DDoS Protection targets distributed denial-of-service attacks, Azure Firewall filters network traffic, Web Application Firewall protects common HTTP(S) web application threats, network security groups apply subnet or interface rules, and Azure Bastion provides managed remote access to VMs. Key Vault stores secrets, keys and certificates with access controls. Defender for Cloud helps evaluate cloud posture and workload protection.

How it works and why

Defender XDR brings together threat signals from Microsoft Defender for Endpoint, Office 365, Identity and Cloud Apps. Defender for Cloud Apps helps govern SaaS usage and app sessions. Microsoft Sentinel is a SIEM/SOAR platform for log analysis and response automation. Understand which product provides which control before designing integrations.

Worked scenario

A malicious OAuth app requesting mailbox permissions belongs in cloud-app governance; a compromised laptop belongs in endpoint detection; a broad incident correlating both may be investigated using XDR and a SIEM.

Practice sequence

  1. Match an attack to the correct Azure protection control
  2. Separate CSPM from workload threat protection
  3. Sketch Defender XDR to Sentinel data flow
  4. Explain a SIEM alert versus a SOAR playbook
  5. Choose a first-response priority in a combined identity/device incident
Watch out

Do not use Sentinel as a substitute for every individual prevention control; it primarily helps detect, investigate and automate response.

SC-900 · Compliance

Purview, data protection and privacy

Visual analogy

Security decides who enters the library; data governance decides which books contain secrets and how long records must be kept.

Concept

Microsoft Purview addresses data classification, sensitivity labels, data loss prevention (DLP), retention, records management, auditing, eDiscovery and insider risk. Compliance Manager provides improvement actions and assessments; a compliance score is a posture indicator rather than proof of legal compliance. The Service Trust Portal provides Microsoft compliance and audit documents subject to access rights.

How it works and why

A sensitivity label identifies and can protect sensitive information. DLP policies seek to prevent inappropriate transmission or use. Retention policies and labels define preservation or disposition schedules. eDiscovery supports legal investigation; audit logs capture relevant activity. Privacy principles include collection limits, appropriate use and transparency.

Worked scenario

Human Resources must label employee records, retain them for an approved period and alert when sensitive files are shared outside the organization. Identity permissions and Purview controls reinforce one another rather than replacing each other.

Practice sequence

  1. Classify a sample dataset as public, internal or confidential
  2. Pick a sensitivity label strategy
  3. Define a DLP rule for external sharing
  4. Specify retention and legal-hold behavior
  5. Identify which audit record would verify a policy action
Watch out

Compliance Score is not a certification that the organization fully meets a law or standard.

SC-900 · Security concepts

How SSO, OAuth, OIDC and SAML differ

Visual analogy

SSO is the experience of using one trusted check-in to enter several venues; the protocol is the language used between the doors.

Concept

SAML commonly carries signed XML assertions for enterprise browser SSO. OAuth 2.0 is a framework for delegated authorization: an application obtains scoped access tokens to call a resource. OpenID Connect (OIDC) adds an authentication and identity layer over OAuth, often through ID tokens. SCIM is a provisioning protocol for creating and deprovisioning users and groups; it is not a sign-in protocol.

How it works and why

Always ask which party is the user, identity provider, application (client) and resource server. An access token is intended for a resource, while an ID token describes an authentication event to the client. Token signature, audience, issuer, lifetime and permissions must be validated. A redirect URI should match a registered value to protect the authorization flow.

Worked scenario

A company integrates a SaaS HR portal using SAML for sign-in and SCIM for automatic staff provisioning. An internal API uses OIDC for login and OAuth tokens to call protected API endpoints.

Practice sequence

  1. Draw the actors of an OIDC authorization code flow
  2. Point to the identity provider and relying party
  3. Label the access token recipient and audience
  4. Choose SAML or OIDC for a sample SSO integration
  5. Explain which part SCIM handles
Watch out

An OAuth access token is not a general-purpose proof of user login to every application.

SC-300 · User identities

Tenant settings, administrative units and roles

Visual analogy

The headquarters controls enterprise-wide policy; regional administrators can receive limited management scope.

Concept

A Microsoft Entra tenant contains directory-wide settings such as default domain, verified domains, user permissions, group settings, device settings and company branding. Administrative units allow selected admins to manage scoped sets of users, groups or devices. A role assignment alone does not prove that an admin has unlimited scope—evaluate role definition, assignment scope and any PIM activation.

How it works and why

In Entra, Global Administrator is powerful and should be tightly limited. Use narrow built-in roles, custom roles where appropriate and just-in-time eligible assignments for high-risk administration. Administrative units scope supported management capabilities; they do not create a separate tenant or automatically isolate every policy.

Worked scenario

A global organization lets a regional Helpdesk Administrator reset eligible accounts inside a regional administrative unit, without granting company-wide identity administrator privileges.

Practice sequence

  1. Inspect tenant settings and verified domain concept
  2. Create a regional administrative unit
  3. Choose a least-privileged role
  4. Assign the role with the intended scope
  5. Verify the scope and document a rollback plan
Watch out

Administrative units cannot substitute for authorization testing on every product and resource.

SC-300 · User identities

Users, groups, licenses and bulk operations

Visual analogy

A user is an employee record; group membership is a department assignment; licensing is a separate service entitlement.

Concept

User lifecycle includes creation, profile updates, authentication method enrollment, group membership, disabling and deletion. Security groups are commonly used for application access and policy targeting. Group types and membership rules matter: manually assigned groups differ from dynamic memberships evaluated from attributes. Licensing may be directly assigned or group-based, depending on available service capabilities.

How it works and why

Bulk tasks use controlled CSV input or Microsoft Graph PowerShell automation. Validate attributes, name collisions, licensing inventory and permissions before processing real identities. A safe automation sequence is inspect, validate, preview changes, apply to a small test group and audit results. Devices may be registered, joined or hybrid joined; these states affect authentication and access decisions.

Worked scenario

A new Finance analyst receives a member account, the Finance-Restricted security group and a suitable service license; disabling the account later should trigger an access review and session revocation if risk warrants.

Practice sequence

  1. Create the employee Avery Lane
  2. Create a Finance-Restricted security group
  3. Add Avery to the group
  4. Compare direct versus group-based license models
  5. Explain how to export audit evidence for the changes
Watch out

A group membership change may not immediately invalidate every token or session; consider revocation and token behavior.

SC-300 · User identities

Custom security attributes and identity classification

Visual analogy

Adding a department label to a badge is not the same as granting clearance to the department.

Concept

Custom security attributes add schema-based attributes to objects for authorization and governance scenarios. Define attribute sets, permitted data types and assignment authorization. They are separate from ordinary profile attributes such as department and from security group membership. They are not automatically a drop-in replacement for access policy targeting.

How it works and why

Before creating attributes, write a controlled vocabulary and decide which service can populate and update values. Apply minimal delegated rights to readers and assigners. Document how an attribute becomes authoritative and how stale or sensitive values will be handled.

Worked scenario

An organization tags approved business applications with a cost-center or risk classification, then uses controlled automation and reviews to keep that metadata accurate.

Practice sequence

  1. Choose a security classification attribute
  2. Define accepted values and who can update it
  3. Apply the attribute to a sample app
  4. Describe a use case in a security workflow
  5. Verify the attribute cannot be casually modified by ordinary users
Watch out

Avoid putting secret values in attributes; metadata can have visibility and logging consequences.

Visual analogy

Visitors can enter a building for one project without becoming permanent employees.

Concept

Microsoft Entra B2B collaboration lets external users access selected organizational resources. Cross-tenant access settings govern inbound and outbound collaboration behavior. Cross-tenant synchronization can automate suitable lifecycle processes between tenant organizations. SC-300 · User identities

Hybrid identity, Connect Sync and Cloud Sync

Visual analogy

Think of a source-of-truth register copied to other offices; you must know which copy is allowed to make edits.

Concept

Organizations with AD DS may synchronize accounts to Entra ID using Microsoft Entra Connect Sync or Cloud Sync, selected according to supported topology and requirements. Password hash synchronization (PHS) lets Entra validate a derived password hash in the cloud; pass-through authentication (PTA) uses on-premises agents. Seamless SSO can reduce repeat sign-ins for suitable domain-joined clients.

How it works and why

Migration away from AD FS requires application inventory, federation dependency evaluation, staged cutover, recovery planning and monitoring. Connect Health provides insights for supported hybrid components. Hybrid troubleshooting begins with source object, sync scope, join rules, attribute conflicts and sign-in method—not simply deleting and recreating identities.

Worked scenario

A 10,000-person company has AD DS accounts and Microsoft 365. You document the authentication source, sync engine, update direction, rollback and alerting before migrating federation.

Practice sequence

  1. Map AD DS and Entra authority for three attributes
  2. Choose PHS or PTA for a scenario
  3. Simulate a duplicate UPN sync issue
  4. Select a reconciliation approach
  5. Write a safe AD FS migration checkpoint
Watch out

Synchronization is not a backup plan; do not treat disabling sync as an instant safe rollback.

SC-300 · Authentication & access

MFA, passkeys, Temporary Access Pass and certificate methods

Visual analogy

A keyless badge is convenient, but the enrollment and recovery process decide whether it is actually trustworthy.

Concept

A passkey based on FIDO2/WebAuthn can resist phishing by binding authentication to the legitimate service origin; Windows Hello for Business uses device-associated cryptographic keys. Microsoft Authenticator, certificate-based authentication, security keys and Temporary Access Pass (TAP) support different enrollment and recovery scenarios. Authentication strengths can require specific methods for sensitive resources.

How it works and why

Roll out passwordless with method eligibility groups, pilot enrollment, platform compatibility, user communication, helpdesk recovery and sign-in audit monitoring. TAP is time-limited bootstrap/recovery access, not a permanent replacement for authentication policy. Administrators should avoid policies that lock every privileged account out; test emergency access paths.

Worked scenario

A new analyst without a registered security key receives an approved one-time TAP, enrolls a passkey on their managed device, then uses the passkey to reach an internal high-value app.

Practice sequence

  1. Inspect authentication methods policy
  2. Enable passkeys for a pilot cohort
  3. Create a TAP for a sample user
  4. Plan a passwordless registration check
  5. Explain why phishing resistance differs from generic MFA
Watch out

Push-based MFA can be vulnerable to fatigue and social engineering; requiring MFA alone does not guarantee phishing resistance.

SC-300 · Authentication & access

SSPR, password protection and session revocation

Visual analogy

When a badge is lost, recovering access must not be easier to attack than the original sign-in.

Concept

Self-service password reset (SSPR) combines policy scope, registered authentication methods and recovery requirements. Entra Password Protection can block weak or custom banned passwords, with hybrid options under documented prerequisites. Administrators need to know the difference between disabling an account, resetting credentials and revoking refresh sessions; token and session behavior can vary across applications.

How it works and why

A safe compromised-account response includes investigating risk, blocking or disabling sign-in as appropriate, resetting credentials, revoking relevant sessions, confirming MFA re-enrollment if needed and validating restored access. Separate ordinary helpdesk recovery from administrator emergency access.

Worked scenario

A risky sign-in is detected from an unfamiliar location. You preserve logs, evaluate whether the user is compromised, revoke sessions and require a secure recovery flow.

Practice sequence

  1. Identify the account-recovery threat
  2. Choose recovery methods and minimum registration
  3. Inspect a flagged sign-in
  4. Revoke mock sessions for the user
  5. Document the intended validation and user communication
Watch out

A password reset alone is not a guaranteed way to instantly terminate every existing application session.

SC-300 · Authentication & access

Conditional Access policies and safe rollout

Visual analogy

A security gate checks WHO, WHAT, WHERE and DEVICE before deciding whether access needs extra proof.

Concept

Conditional Access policies evaluate assignments (users/groups and resources), conditions (such as locations, device platforms or risk) and access or session controls. Policies apply together; a matching block policy blocks access, and requirements from applicable grant policies must be satisfied. Exclusions and emergency access design are critical. Policy outcomes can differ from simply choosing one rule, so validate with What If and sign-in logs.

How it works and why

A production rollout should define the business case, exclusions, expected sign-in impact, license prerequisites, pilot group, report-only observation period, support plan and rollback criteria. Report-only shows impact without enforcing most grant decisions. When deploying risk-based policies, confirm appropriate licensing and sign-in/user risk data availability.

Worked scenario

Finance access from unmanaged devices should require stronger authentication, and high-risk events may be blocked. Start with a finance pilot in report-only before an approved staged rollout.

Practice sequence

  1. Create Finance-Restricted users and sample app
  2. Build a finance MFA Conditional Access policy
  3. Set it to report-only
  4. Run What If with different users and device states
  5. Verify block precedence and document what would happen before enabling
Watch out

Do not create an all-users block policy without carefully planned emergency access and validated exclusions.

SC-300 · Authentication & access

Authentication context, protected actions and session controls

Visual analogy

Not every room in a building needs the same check; a vault door can require stronger verification mid-visit.

Concept

Authentication context can mark specific application actions or resources for higher assurance. Protected actions in Entra can require a Conditional Access authentication context before selected administrative actions. Session controls include sign-in frequency, persistent browser behavior and integrations to control access in compatible applications. Continuous access evaluation (CAE) can help supported resources react to certain changes more rapidly.

How it works and why

Use app-owner requirements to determine which operations justify step-up authentication. Verify app and client compatibility, how controls are invoked, and what logs reveal. Not all apps or token flows support every session feature. Avoid turning a sign-in control into an application authorization substitute.

Worked scenario

Employees may use basic authentication strength for viewing expense reports but require phishing-resistant authentication when exporting sensitive payroll data.

Practice sequence

  1. Identify high-value protected action
  2. Define desired authentication strength
  3. Sketch context to policy evaluation path
  4. List app and client compatibility checks
  5. Choose session control and evidence to confirm behavior
Watch out

CAE is not universal instantaneous revocation in every app and token scenario.

Identity Protection: users, sign-ins and workload risk

Visual analogy

A security officer distinguishes a stolen badge (user risk) from a suspicious entrance attempt (sign-in risk).

Concept

Microsoft Entra ID Protection can identify certain risky user and sign-in patterns. User risk represents the likelihood an identity is compromised; sign-in risk focuses on an authentication attempt. Responses may include remediating risky users, investigating events and applying risk-based Conditional Access controls. Risk detection visibility and automatic policies depend on licensing.

How it works and why

For each event, assess who, when, source IP/location, device, client application, authentication method and Conditional Access result. Preserve evidence; distinguish false positives from confirmed compromise. Workload identity risk also matters when service principals or automation identities become suspicious.

Worked scenario

A payroll admin has impossible-travel alerts. The correct investigation correlates the sign-in records, associated device and access changes before declaring the account compromised.

Practice sequence

  1. Open the seeded risky sign-in
  2. Identify three meaningful suspicious signals
  3. Choose triage and response severity
  4. Record an investigation conclusion
  5. Explain how risk-based Conditional Access could remediate
Watch out

A risky sign-in is a risk signal, not definitive proof of a successful breach.

SC-300 · Workload identities

Service principals, managed identities and Azure resource access

Visual analogy

A background service needs its own badge; borrowing an employee’s password creates risk and accountability problems.

Concept

An app registration describes an application identity configuration. A service principal is its local enterprise representation in a tenant. Managed identities are Azure-managed workload identities used by supporting Azure services, reducing credential management overhead. System-assigned identities are tied to the lifecycle of their resource; user-assigned identities may be reused by resources.

How it works and why

Authorization still matters: identity creation does not automatically grant API, storage or Key Vault permissions. Assign the least-privilege Azure RBAC role or resource-specific permissions at the smallest workable scope. Monitor identity usage and avoid static secrets where a supported federation or managed identity option exists.

Worked scenario

A scheduled Azure function reads a single Key Vault secret. Give its managed identity only the necessary vault permissions, not Contributor to the subscription.

Practice sequence

  1. Compare a user account, service principal and managed identity
  2. Create a mock managed identity
  3. Associate it with a sample Azure resource
  4. Choose least-privilege resource permission
  5. Validate access and log intended behavior
Watch out

A managed identity is not a universal credential usable from any machine without a supported trust or federation design.

Visual analogy

An app asking for access to every mailbox is not equivalent to a user consenting to read only their own calendar.

Concept

Microsoft Graph applications request delegated scopes on behalf of signed-in users or application permissions running without a user. SC-300 · Identity governance

Access reviews and least-privilege recertification

Visual analogy

A visitor list becomes unsafe when former visitors keep keys indefinitely.

Concept

Access reviews help designated reviewers reassess memberships or application entitlements. Scope, reviewers, recurrence, decision handling, auto-apply behavior, notification and evidence all require deliberate design. This is an operational governance process; a periodic review cannot replace immediate termination response.

How it works and why

Go from simulation to authentic Entra administration

This companion teaches you how to practice safely in a separate test tenant with an evidence trail. It cannot create a Microsoft tenant, license, or production resource on your behalf. Complete simulated labs first.

Important: avoid unapproved costs and lockouts.

Microsoft Entra Free may support foundational users and groups, but Conditional Access generally requires P1 and risk-based policies/PIM generally need P2 or applicable governance licensing. Azure resources, Log Analytics data, or premium services can incur charges. Free developer E5 sandboxes require eligibility and are not universally available. Never activate a trial, subscription, or purchase automatically.

For any change, work in a dedicated authorized test tenant. Maintain tested emergency access accounts. Use report-only Conditional Access during evaluation. Don't grant broad rights or test global blocking policies in production.

Real-tenant guided labs

01 · Prepare a secure test tenant Foundation

Learning goal: Explain tenant separation, administrative authority, and emergency recovery before doing any account or policy management.

Prerequisite: An authorized test tenant, an administrator assigned by its owner, and written confirmation that no paid trial or subscription activation is needed.

Identify your test directory.

Open entra.microsoft.com. Observe tenant name, directory ID, and administrative roles without copying identifiers into public materials. Why: you must know the boundary you are modifying.

Inspect emergency-access guidance.

Design at least two cloud-only, separately monitored emergency identities according to policy, with appropriate phishing-resistant methods. A learner should not create unapproved Global Administrators. Why: access recovery must survive identity outages and misconfigured policies.

Document licensed features.

Compare current tenant entitlements with Microsoft’s licensing page. Why: seeing a portal blade does not necessarily mean you can deploy a paid feature.

Evidence: Sanitized tenant-architecture diagram, role inventory, emergency-access test strategy, and cost decision. Rollback: None; this lab is read-only unless you have an explicitly approved procedure.

02 · User, group and role lifecycle Free-tier concepts

Learning goal: Differentiate user identities, security groups, tenant admin roles, and application permissions.

Create a fictional learner account.

In the test tenant go to Identity → Users → All users → New user. Use a training-only address and a department. Why: a directory user object is an identity record, not an entitlement.

Create and populate a security group.

Go to Identity → Groups → All groups → New group; choose security group, then add the new user. Why: group-based targeting simplifies the lifecycle and review.

Verify the relation in both directions.

Inspect the user’s group memberships and the group’s members. Then remove the test user. Why: effective assignment must reflect actual directory state.

Inspect role requirements without elevating privileges.

Read the Microsoft Entra role descriptions. Contrast User Administrator, Groups Administrator, Cloud Application Administrator and Global Administrator. Why: principle of least privilege requires choosing the appropriate authority.

Expected: User membership is visible after assignment and absent after removal. Troubleshoot: Check whether you are editing the correct tenant, group type, and object. Cleanup: Delete dedicated lab identities and groups when approved.

03 · Conditional Access safely in report-only mode P1+ usually required

Prerequisite: Test-only Microsoft Entra ID P1 rights (or entitled equivalent), Conditional Access Administrator or equivalent least privilege, and approved emergency-access design. If the license is unavailable, perform the equivalent task in V6 simulator instead.

Plan a narrow target.

Choose a dedicated lab group and one lab application. Verify emergency access arrangements before enforcing any broad policy. Why: rollouts must be reversible.

Create a policy.

Open Protection → Conditional Access → Policies → New policy (navigation can vary). Set intended lab users and app, a suitable grant control, and Report-only. Do not enable it globally.

Test with What If and sign-in logs.

Check one in-scope and one out-of-scope test identity. Why: report-only indicates prospective impact; actual enforced policies remain independent.

Prepare a rollback.

Document the policy ID, targeted groups, expected outcome and the process to disable or remove the lab-only policy. Do not turn the policy on without reviewed authorization.

Troubleshoot: Scope, apps, inherited policy decisions, authentication strength, group membership, device claims, and license. Evidence: Sanitized report-only outcome versus expected result.

04 · Phishing-resistant sign-in and recovery Device + license dependent
Identify authentication strength.

Compare a password, SMS OTP, Microsoft Authenticator, and FIDO2 passkey. Explain why origin binding differs from a relayed one-time code.

Plan a small registration pilot.

Open Protection → Authentication methods in your lab tenant, note permitted methods, registration policies, and required hardware. Do not change a production-wide policy.

Design verified recovery.

Study Temporary Access Pass: permitted scope, time limit, identity verification and one-time/multi-use behavior. Never distribute an actual TAP in a public portfolio.

Document failure and recovery.

Test only with your isolated authorized lab account. Explain lost-device recovery, session revocation, and how to confirm successful phishing-resistant sign-in.

Evidence: Sanitized method policy and conceptual challenge-response diagram. Cleanup: Delete temporary lab credentials, reset test method registrations where appropriate.

05 · App registration and least-privilege API access Separate test app
Create a dedicated test app registration.

Open Identity → Applications → App registrations → New registration in an authorized test tenant. Use a fictional display name, supported account type, and a valid local/test redirect URI if needed.

Observe enterprise app representation.

Locate the app’s service principal under Enterprise applications and explain why the two directory objects are different.

Study Graph API permissions safely.

Compare delegated and application permissions and the admin-consent process. Do not grant tenant-wide application permissions in a real tenant without approval.

Inspect token flow diagrams.

Identify authorization code, client credentials, scopes, resource audience, and consent. Do not record real tokens or secrets in a portfolio.

Troubleshoot: Wrong redirect URI, wrong tenant, missing consent, incorrect delegated/application type, or missing app assignment. Cleanup: Delete the lab registration and related objects after confirming no dependencies.

06 · Guest collaboration and entitlement lifecycle Licensing varies
Review external collaboration settings.

Open Identity → External Identities and understand invitation policy, cross-tenant access, and trust decisions. Never invite unapproved external addresses.

Design a guest request.

Describe the partner identity provider, local guest object, resource group, sponsor, approver, expiration and ownership. If authorized, use a test-only identity.

Review access governance.

Inspect access packages and access reviews where licensed. Record the decision and whether deny/revoke is applied to actual entitlements.

Revoke safely.

Remove simulated or authorized lab access and confirm that the application actually becomes unavailable. Why: a review without enforced remediation is incomplete governance.

Troubleshoot: Invitation redemption, cross-tenant restrictions, app assignment, review decision application, and guest lifecycle.

07 · Troubleshoot sign-in evidence and KQL Export may incur cost

Prerequisite: Read-only access to test sign-in logs. An Azure Log Analytics workspace is optional and may charge for ingestion or retention; do not create one without permission.

Inspect a fictional failed sign-in.

Open Identity → Monitoring & health → Sign-in logs. Identify request time, application, result, device, conditional access status, and correlation ID.

Separate log types.

Understand when to read sign-in logs, audit logs, and provisioning logs. Why: each describes a different control plane event.

Practice a sample KQL query on synthetic data.
SigninLogs
| where TimeGenerated > ago(24h)
| summarize Failures=countif(ResultType != "0")
    by UserPrincipalName

Why: summarize failures by user; this query requires correctly ingested SigninLogs data in a suitable workspace.

Write a root-cause summary.

State hypothesis, supporting evidence, the relevant policy, safe remediation, and how success will be verified.

08 · Enterprise identity architecture capstone Portfolio

Scenario: A fictional 6,000-person organization has two regions, an on-premises Active Directory, 700 external collaborators, critical Finance and HR applications, 12 privileged admins, and new internal AI agents. Management requires phishing-resistant sign-in, staged migration, cost control, and proof of recoverability.

Produce a current-state diagram.

Map identities, tenant boundaries, authentication paths, trust decisions, applications, protected data, monitoring, and privileged access.

Write future-state architecture.

Choose identity synchronization, user authentication, app integration, external access, least privilege, agent governance, logging, and compliance controls.

Build migration and rollback phases.

Specify pilot sizes, policy report-only checks, emergency account validation, sign-in metrics, integration dependencies, cutover and rollback criteria.

Deliver an executive summary.

Explain three priority risks, the chosen controls, business impact, tradeoffs, cost/licensing assumptions, measurable outcomes, and residual risks.

Mastery evidence: 2 architecture diagrams, 1 risk register, 1 migration runbook, 1 rollback plan, 1 incident investigation, 1 security decision record and a 6-slide executive briefing. This is a portfolio exercise, not proof of SC-100 exam readiness.

What to practice next
